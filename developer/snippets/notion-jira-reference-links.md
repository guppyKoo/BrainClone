# 노션·피그마·Jira를 코드에서 참조할 때 실제로 깨진 것들

> Edu Vibe 양쪽 레포의 `docs/references.md`를 쓰면서 실제로 물린 것들.
> 원천 문서가 사내 노션·피그마·Jira에 있고 AI가 그걸 읽어 작업하는 구조라면 어디서든 같은 곳에서 걸린다.

## 1. 노션 링크는 `/p/`가 붙은 것만 열린다

```
https://app.notion.com/p/{32자 hex}            페이지·행
https://app.notion.com/p/{32자 hex}#{블록id}    블록 앵커
```

**SQL(데이터소스 쿼리)로 얻은 행 `url`에는 `/p/`가 없고, 그 형태는 열리지 않는다.**
이 형태를 그대로 붙여 PR의 API 명세 링크 5개가 전부 깨졌다.

| | |
|---|---|
| 깨진다 | `https://app.notion.com/3bc4e6997fb081cb8f2bf458b67df3ef` |
| 열린다 | `https://app.notion.com/p/3bc4e6997fb081cb8f2bf458b67df3ef` |

`fetch`가 돌려주는 `url` 필드와 `<page url="...">`는 `/p/` 형태이므로 그쪽을 쓴다.
SQL 결과를 쓸 때는 `/p/`를 넣어 정규화한다.

## 2. 링크는 가리킬 수 있는 가장 좁은 단위로 — 단 구조마다 한계가 다르다

| 구조 | 붙일 수 있는 것 |
|---|---|
| 데이터베이스 | **행(=페이지) 링크** |
| synced block | **블록 앵커**(`...#블록id`) |
| 일반 헤딩 | 없음 — 페이지 링크 + 절 이름을 글로 쓴다 |

**일반 헤딩의 블록 링크는 도구로 얻을 수 없다.** 노션 MCP가 synced block과 데이터베이스 행에만 id를 노출하고
헤딩 블록 id는 응답에 없다. 브라우저에서 «블록 링크 복사»로 직접 가져오지 않는 한 방법이 없으므로,
그때는 페이지 링크에 절 이름을 덧붙이는 선에서 멈춘다.

행 링크를 찾는 방법 — 데이터베이스를 `fetch`해 `<data-source url="collection://...">`를 얻고,
그 URL을 테이블 이름으로 SQL을 돌리면 행마다 `url`이 나온다.

## 3. 붙인 링크는 하나씩 열어본다 — 형태만 맞고 다른 문서를 가리키는 경우가 있다

피그마 `node-id=164-7958`이 「로그인」인 줄 알았는데 실제로는 「2. 학급 홈 - 프로젝트」 섹션이었다.
**확인하지 않은 anchor는 없는 것보다 나쁘다** — 리뷰어를 엉뚱한 화면으로 보내고, 그 화면을 근거로 읽게 만든다.

노션은 `fetch`에 넣어 제목이 기대한 것과 같은지 보면 된다.

## 4. 컴포넌트의 «변형이 몇 가지인가»는 화면 파일이 아니라 컴포넌트 파일에서 읽는다

화면 파일에는 그 컴포넌트가 쓰인 **한 장면**만 있어서, 없는 변형을 «없다»고 단정하기 쉽다. 실제로 둘 —

- 「설정 메뉴」의 변형은 **권한 셋**뿐이고 화면 크기 변형이 없다. 즉 같은 권한이면 반응형이든 아니든 구성이 같아야 한다.
- 작업공간 상단바의 폭 562·688 변형도 **채팅이 옆에 붙은 데스크톱 상태**였다. 375 모바일 아트보드의
  상단바 인스턴스 21개는 **전부 비어 있어** 992 미만 상단바는 시안에 아예 없다.
  **폭만 보고 «반응형 시안»으로 읽으면 틀린다.**

## 5. Jira MCP를 다룰 때

- **`cloudId`는 도메인(`{org}.atlassian.net`)을 그대로 넣으면 된다.** UUID를 따로 찾지 않아도 된다.
- **상태 변경은 이름이 아니라 전이(transition) id로 한다.** id는 워크플로가 바뀌면 달라지므로,
  옮기기 전에 그 이슈의 전이 목록을 먼저 조회한다.
- AI 권한 경계를 이렇게 갈랐다 — **조회·상태 변경·코멘트는 바로, 이슈 생성·삭제는 확인받고.**
  생성·삭제만 확인을 거치는 이유는 되돌리기 어렵고 스프린트 계획과 남의 보드에 바로 드러나기 때문이다.
  상태 변경은 되돌릴 수 있고 실제 진행을 반영하는 것이라 미루면 오히려 보드가 낡는다.
- **PR 제목에 Jira 키를 쓰지 않으면 브랜치 이름이 태스크와 코드를 잇는 유일한 끈이 된다.**

## 6. 문서 종류마다 AI의 쓰기 권한이 다르다

| 문서 | 권한 |
|---|---|
| 기획 문서 | **읽기 전용.** 어긋난 것을 발견해도 고치지 않는다 |
| 테크스펙(스키마·API 명세) | **코드와 함께 갱신하는 것이 규칙.** 단 구조를 바꾸는 결정은 적기 전에 합의 |

기획 문서를 읽기 전용으로 둔 이유는 그것이 기획·디자인·개발이 합의한 결과이고, 그 합의가 이 레포 밖의
다른 기능·담당자에게도 걸려 있기 때문이다. **문서를 먼저 고치면 논의 없이 합의가 바뀌고,
틀린 방향이었을 때 되돌릴 근거도 사라진다.** 그래서 순서를 이렇게 고정했다.

1. 코드·데이터로 사실을 먼저 확인한다 (문서가 틀린 건지, 내가 잘못 읽은 건지)
2. 어긋난 지점과 근거를 PR 본문에 «확인 필요»로 적어 기획자 확인을 요청한다
3. **확인 전까지는 기획 문서를 따르고 코드도 임의로 바꾸지 않는다**

실제로 그렇게 처리해서 이득을 봤다 — 학급 홈 접근 권한이 요구사항과 라우트 표에서 갈려 보여
PR에 «확인 필요»로 올렸고, 확인 결과 기획 문서의 전제 조건이 맞았다.
**문서를 먼저 손댔다면 맞는 쪽을 지웠을 것이다.**

## 7. 원천 문서라도 그대로 믿지 않는다

노션이 원천이지만 코드와 어긋난 적이 있고, 둘 다 예외가 아니라 **조용히 잘못 동작하는 형태**였다.

- API 명세의 입장코드 예시가 `"ABC123"`이었지만 실제 검증은 `^[A-Za-z]{5}$`라 숫자가 들어가지 않는다.
- `User` 식별자가 문서·데이터·코드에서 `id`/`_id`로 갈려 교사 로그인이 401만 냈다.

**계약을 문서에서 읽었으면 실제 응답이나 데이터로 한 번 확인한다.**
어긋난 것을 발견하면 어느 쪽이 맞는지 정하고 **양쪽을 함께 고친다** — 한쪽만 고치면 다음 사람이 같은 곳에서 다시 막힌다.
