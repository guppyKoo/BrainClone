# 결정: 강의 공개 기간 검증 정책

교육과정 편집 V2(`TeachConsoleApp/edit-lecture-v2`)에서 공개 기간 검증을
어디까지 하고, 비공개 강의는 어떻게 다룰지에 대한 판단.
데이터 계약 자체는 [[edu-lesson-period-contract]]에 분리해 두었다.

## 맥락 — 왜 건드렸나

두 가지가 동시에 신고됐다.

1. **데드락**: 공개 기간에 마감만 입력하면 저장이 막히는데, 비공개로 전환해도
   여전히 막힌다. 비공개에서는 기간 UI가 `{lessonOpen && ...}`로 숨겨져
   사용자가 고칠 방법이 없다.
2. **조용한 사고**: "항상 공개" 체크를 끄고 날짜를 하나도 안 넣어도 저장이 된다.
   그러면 `time_set: true` + 날짜 null이 저장되는데, 서버 `isOpenTime`은 이 조합을
   항상 '닫힘'으로 판정한다. 교사 화면에는 "공개"로 보이지만 학습자는 강의를
   열지도 수강하지도 못한다.

`isValidOpenPeriod`에 `// 미입력 (저장 게이트가 별도 차단)`이라는 주석이 있었지만
**그 게이트는 존재하지 않았다.** 수강 가능 기간에만 있었고 공개 기간에는 빠져 있었다.

## 결정

| # | 결정 | 근거 |
|---|---|---|
| D1 | 공개 상태에서 기간 미입력이면 저장 차단, 토스트 "공개 기간을 입력해주세요" | `time_set: true` + 날짜 null 조합을 원천 차단 |
| D2 | 공개 상태에서 "마감만" 입력은 계속 차단 | 서버는 허용하지만 시작 없는 공개 기간은 의도가 모호 (제품 결정) |
| D3 | 비공개면 공개 기간·수강 가능 기간 검증을 하지 않음 | 비공개 강의에서 기간은 열람·수강 판정에 영향이 없고, UI가 숨겨져 고칠 수단이 없음 |
| D4 | 비공개여도 기간 값은 보존 | 다시 공개로 켤 때 복원하기 위함 |
| D5 | 단, 기록할 날짜가 하나도 없으면 `time_set: false`로 정규화 | 복원할 값이 없는 경우에만 적용되므로 손실 없이 무효 조합을 차단 |

D2는 서버 규칙보다 프론트가 **더 엄격한** 경우다. `isOpenTime`의 세 번째 절이
마감만 설정된 상태를 열림으로 인정하므로, 이 차단은 기술적 제약이 아니라 제품 판단이다.
주석에 그렇게 명시해 두었다.

## 기각한 대안

**(A) 비공개일 때도 기간 UI를 노출하고 검증은 그대로 유지**
사용자가 잘못된 상태를 보고 고칠 수 있게 하자는 안. 규칙이 단순해지는 장점이 있었으나
비공개 강의에 공개 기간 UI가 보이는 게 정보 구조상 어색하고, 무엇보다 **레거시 오염
데이터를 사용자가 일일이 손으로 고쳐야 한다.** D5는 저장 한 번으로 자동 치유된다.

**(B) 비공개면 기간 필드를 전부 null로 저장**
내가 처음 제안한 안. "비공개면 기간은 의미 없으니 지우자"는 논리였는데,
사용자가 **다시 공개로 켤 때의 복원**을 요구사항으로 제시해 기각했다.
`isOpenTime`이 `isPrivate`를 보지 않으므로 비공개인 동안 기간 값이 남아 있어도 무해하다.

**(C) 토글 전환 시점에 기간 값 초기화**
기존 `handleToggleLessonOpen`이 수강 가능 기간에 쓰던 방식. 실수로 비공개를 눌렀다
되돌리면 입력하던 값이 날아가고, 무엇보다 **토글을 거치지 않고 로드되는 레거시
데이터를 구제하지 못한다.**

## 무엇이 바뀌면 이 판단이 무효가 되나

- `isOpenTime`이 `isPrivate`를 함께 보게 되면 D3·D4의 전제가 사라진다
- 비공개 강의에서도 기간 UI를 노출하도록 디자인이 바뀌면 D3의 근거(고칠 수단 없음)가 사라진다
- v1 편집기가 폐기되면 [[edu-lesson-period-contract]]의 호환 제약 대부분이 풀린다
