# 결정: eval의 산출물은 판단이 아니라 계측값이다

같은 날 작성한 [[2026-09-16-edu-vibe-eval-gate-reporting]]의 후속이다. Gate 분리까지는
"품질 점수를 어떻게 정확히 낼 것인가"의 문제였고, 이 문서는 **그 점수가 무엇을 주장할 수 있는가**를
좁힌다.

## 배경 — 외부 관점에서 무너진 지점

구현이 진행된 뒤 "제3자 개발자가 이걸 보면 어떻게 생각하겠는가"를 검토했고, 다음이 드러났다.

- 같은 날 제품 코드는 한 줄도 바뀌지 않았는데 Q1 평균이 **0.697 → 0.871 → 0.929 → 0.835**로 움직였다.
  전부 평가기 버전(`r-v4.2` → `v5` → `v6` → `v7`) 변경 때문이다. 변동폭 0.23.
- 표본 26턴은 **대화 체인 6개**뿐이고 같은 체인 안 턴은 독립이 아니다. 실질 n은 6에 가깝다.
- 채점 턴의 **41%가 `page text includes "X"` 검사 하나**로 Q1=1을 받는다. 사실상 스모크 테스트다.
- `L`과 두 Ambiguity가 **26/26 전부 null**이라 리포트 12개 차트 중 6개가 빈 차트이고 필터는 장식이다.
- 사람이 라벨링한 기준셋이 없어 Q가 사람의 품질 판단과 같은 방향인지 검증된 적이 없다.

## 결정

**1. 산출물의 주장 크기를 "계측값"으로 낮춘다.**
좋다/나쁘다 판단은 데이터를 보는 사람이 한다. 도구는 수집과 계산만 한다.
"제품 품질은 0.83"이 아니라 "이 조건에서 이렇게 읽혔다"가 이 도구가 지지할 수 있는 최대 주장이다.

**2. LLM = Extractor 계약을 규약이 아니라 코드와 테스트로 강제한다.**
- `buildExtractorInput`이 대화 맥락에 섞여 들어온 현재 턴의 답변·결과 HTML을 경계에서 지운다.
  importer 구현에 의존하지 않는다.
- 모델이 `S`·`checks`·`scores`를 출력해도 무시한다. `S = requirements.length`, 검사 DSL은 컴파일러가
  만들고 모든 검사는 코드가 `required: true`로 고정한다. 모델이 채점 분모를 줄일 수 없다.
- `description` 같은 자유 서술은 어떤 점수에도 영향을 주지 않는다. `test/extractor-role.test.ts`가
  서술만 바꿨을 때 Q2·Q3가 동일함을 검증한다.

**3. 변경 허용 여부를 R에서 역추론하지 않고 `changeScope`로 명시 선언한다.**
R은 Q1 검증용 술어인데 코드가 그것을 변경 예산으로 몰래 읽고 있었다. 그래서 판단 주체가 없었다.
`{ kind: REPLACE_ALL | TARGETED | ADDITIVE, preserve: Target[], regions: Target[] }`을 발화에서 추출한다.
결과물을 보지 않고 발화만으로 정하는 분류이며 점수가 아니다.

**4. "요구 미충족"과 "측정 불가"를 분리한다.**
- `NOT_OBSERVABLE`: 계약은 실행됐지만 관측 대상이 화면에 없음. Q1 분모에서 제외한다.
- 행동은 결과 상태에 도달하기 위한 수단이지 요구가 아니다. 행동 대상이 없을 때 변화 단언은
  `NOT_OBSERVABLE`, 절대 단언은 행동을 건너뛰고 결과만 관측한다.
- 비교할 값이 계약 슬롯에 없는 문자열 단언은 컴파일러가 `UNSUPPORTED_PROBE`로 거절한다.

**5. DSL 구멍을 닫힌 코드로 분류하고 컴파일러 거절과 분리한다.**
`unmapped`(LLM이 표현 실패)와 `rejected`(컴파일러가 계약 위반으로 거절)는 고쳐야 할 곳이 다르다.
`summary.json.dslGaps`가 코드별 빈도를 집계해 스키마 확장 우선순위를 숫자로 만든다.

**6. 모집단 이탈을 평균과 같은 자리에 기록한다.**
`summary.json.population`. 평균만 떼어 읽으면 어려운 턴이 빠져나가 오른 값을 품질 향상으로 오해한다.

## 근거가 된 실측

- `83eaf711` "이거 다 지우고 카트라이더 만들어줘": `TARGETED`로 채점하면 Q2=0.545 / Q3=0.000이고,
  이는 "지우라고 한 11개 중 6개가 우연히 살아남았다"는 뜻이다. **지시를 완벽히 따르면 Q2=0**이 된다.
  `REPLACE_ALL`로 선언하면 Q2=null(보존 요구 없음) / Q3=1.000이 된다.
- `5bc1921b`: 요청한 메뉴 6개가 화면에 전부 있는데 추출기가 변경 전 HTML에서 딴 `#tue`를 골랐고
  AI가 구조를 바꾸면서 그 id가 사라져 6개 전멸 → Q1=0. 계약 거절과 `NOT_OBSERVABLE` 도입 후 Q1=null.
- `0c71eeba`: `boundingBox` 관측을 `greater-than`이 숫자로만 읽어 105×105 타일이 FAIL이었다.
  면적 환산으로 수정.

## 기각한 대안

- **`description`에서 기대값 추출**: 통과 불가능한 검사를 살릴 수 있지만 LLM 자유 서술이 채점에
  직접 들어온다. 계약의 근간이 무너지므로 기각. 대신 컴파일러가 거절하고 프롬프트로 가르친다.
- **행동 대상 부재를 FAIL로 유지**: 추출기가 가정한 조작 수단이 없다는 이유로 이미 충족된 요구를
  0점 처리한다. 실측(`5bc1921b`)으로 false negative가 확인되어 기각.
- **Q3를 대시보드에서 제거**: 계측기라면 채널이 낮게 읽히는 것도 데이터다. 제거 대신 성숙도 표시.
- **cascade 흡수만으로 Q3 해결**: D의 39%가 레이아웃 파생이라 크게 오를 것으로 예상했으나 실측
  결과 **0.361 → 0.375 (+0.014)**에 그쳤다. 그 레이아웃 변화 대부분이 애초에 허용된 변화가 없는
  요소에 붙어 있어 상속할 것이 없었다. 흡수 자체는 옳아 남겼지만 주원인이 아니었다.
- **전면 교체 요청을 `TARGETED`로 두기**: 지시를 따를수록 Q2가 떨어지는 역전이 발생하므로 기각.

## 남은 것 — 계측기의 조건

판단을 하지 않는 대신 **읽은 값이 정확하고 재현되고 단위가 고정**돼야 한다. 세 가지가 미해결이다.

- **재현성 통제**: 추출(불안정)과 측정(결정론적)을 분리해 plan을 버전 관리되는 산출물로 만드는 방향.
- **오차 명시**: 점수에 `±`를 붙이는 대신 "얼마나 측정했는가"(커버리지)를 함께 내보내는 방향.
- **단위 안정화**: `S`를 LLM이 정하므로 Q1의 눈금 간격이 턴마다 다르다. 분수 대신 분자·분모를
  그대로 내보내는 방향.

버전 간 비교 가능성은 개발 단계에서는 우선순위가 낮다고 판단했다. 다만 평가기 버전을 레코드에
찍고 다른 버전의 값을 같은 축에 섞지 않는 최소 규칙은 유지한다.

## 무엇이 바뀌면 이 판단이 무효인가

- 기준셋에서 Q1이 사람의 충족 판정과 어긋나면 `page text` 프록시 비중(41%)부터 다시 설계해야 한다.
- 추출 분산이 크게 측정되면 plan 산출물 분리는 선택이 아니라 필수가 된다.
- `L`·Ambiguity 파이프라인이 채워지면 비어 있는 축 6개가 살아나고 리포트 구성을 다시 판단해야 한다.

## 변경 이력

- 2026-09-16: 최초 작성. 계측기 프레이밍 전환, Extractor 계약의 코드 강제, `changeScope` 명시 선언,
  `NOT_OBSERVABLE` 도입, DSL 구멍 코드 분류 확정

## 추가 결정 — 계측기의 조건을 구현하다 (2026-09-16)

위 "남은 것" 세 가지를 구현하고, 버전 간 비교는 범위에서 뺐다.

### 버전 간 비교는 하지 않는다

앞 절에서 "평가기 버전을 레코드에 찍고 다른 버전의 값을 같은 축에 섞지 않는 최소 규칙은 유지한다"고
적었으나 이를 철회한다. 개발 중 테스트이므로 버전 비교 자체가 필요 없다는 판단이다.
버전 스탬프는 이미 레코드에 들어 있으나 그것을 근거로 한 규칙·고정 코퍼스·CI 델타는 만들지 않는다.

### 재현성 — 층을 나눠 각각 다르게 다룬다

- **실행 층**: 난수 seed만 고정돼 있었고 **시계가 열려 있었다.** 급식표·시간표류 결과물은 실행 시각을
  읽어 화면을 만들므로 같은 결과물이 날마다 다른 점수를 받을 수 있었다. 시계를 2025-03-03 09:00 KST로,
  타임존·로캘을 `Asia/Seoul`/`ko-KR`로 고정했다.
  주입 방식도 `setContent` 직전의 `page.evaluate`에서 `addInitScript`로 바꿨다. 전자는 문서 교체 시점에
  따라 사라질 수 있고, 지금까지 우연히 살아남고 있었을 뿐이다.
- **추출 층**: LLM 원본 출력을 `data/plans/<turnId>.json`으로 고정하고 입력 해시가 같으면 재사용한다.
  저장하는 것은 모델 출력뿐이고 계약 검사·거절 판정·check 생성은 코드가 매번 다시 하므로,
  컴파일러를 고쳐도 재추출이 필요 없다.

**측정 결과**

- 실행 분산: 24턴 × 5회 재실행에서 검사 뒤집힘 **0/47**, 점수가 흔들린 턴 **0/24**. LLM 호출이 없어 비용 0.
- 추출 분산: 같은 로그·같은 프롬프트(`r-v7-change-scope`)·같은 컴파일러(`compiler-v5`)로 돌린 두 배치에서
  **Q1 평균 0.835 → 0.735, Q2 0.718 → 0.775, Q3 0.361 → 0.550.** 제품은 하나도 바뀌지 않았다.

이 대비가 이번 작업의 핵심 근거다. 측정은 이미 완전히 재현되고, 흔들리는 것은 전부 추출이다.
따라서 "점수 차이를 제품 변화로 읽으려면 추출을 고정해야 한다"는 것이 추정이 아니라 관측이 됐다.

### 오차 — `±`가 아니라 `completeness`

추출을 고정하면 측정 오차는 0에 수렴하므로 `±`는 붙일 대상이 없다. 남는 불확실성은 "얼마나 쟀는가"다.
`completeness = { checksNotObservable, checksErrored, checksUsingFallbackTarget, dslCoverage }`를
점수 옆에 함께 낸다.

### 단위 — 분수 대신 분자와 분모

`S`를 추출기가 정하므로 Q1의 눈금 간격이 턴마다 다르다. 어느 쪽이 옳은 가중치인지 정하지 않고
`counts`(턴별 분자·분모)와 `totals`(`macro` 턴 평균, `micro` 요구 합산)를 함께 내보낸다.
두 값의 차이 자체가 "요구를 많이 뽑은 턴이 잘했는가"에 대한 정보다.

### 난이도 L — 단일 스칼라를 만들지 않는다

비어 있던 `L`·Ambiguity 축을 채우는 방법으로 **새 LLM 판단 단계를 넣지 않았다.** Extractor 계약을
깨지 않으면서 측정 가능한 사실만 남긴다.

- `demand` = `requirements`, `probeKinds`, `maxActionSteps`, `requirementsNeedingAction`, `changeScopeKind`
- 각 R에 `source`(`UTTERANCE` | `CONTEXT`)를 붙인다. 판단이 아니라 입력 안의 출처 표시이므로
  추출기가 낼 수 있고 R을 읽는 사람이 검증할 수 있다. 여기서 맥락 의존도가 나온다.
- **1~5 난이도 스칼라는 만들지 않는다.** 축 사이 가중치를 정할 근거가 없다. 축을 따로 두면
  "요구는 많지만 전부 존재 확인"과 "요구는 둘이지만 6단계 조작이 필요"가 구분된다.
- 값이 없는 축의 그래프는 리포트에서 감춘다. 빈 그래프는 "측정했는데 결과가 없다"로 읽혀
  측정하지 않은 사실을 가린다.

### 기각한 대안 (추가)

- **`page.evaluate` 주입 유지**: 실험상 동작하지만 `setContent`가 문서를 교체하는 방식에 의존한다.
  보장되지 않는 동작에 재현성을 걸 수 없어 `addInitScript`로 교체.
- **plan 파일에 컴파일된 check까지 저장**: 컴파일러를 고칠 때마다 전 건 재추출이 필요해진다.
  모델 원본만 저장하고 코드 처리는 매번 재실행하는 쪽을 택했다.
- **프롬프트 버전이 다르면 저장된 추출을 무효화**: 원칙적으로는 옳지만 프롬프트 반복 수정 때마다
  전 건 재추출을 강제해 분리의 이점을 없앤다. 입력 해시만으로 재사용하고 버전은 기록만 한다.
- **난이도 가중합(L = w1·S + w2·probe종류 + …)**: 가중치에 근거가 없다. 숫자가 생기면 근거 없이
  비교가 시작되므로 만들지 않는다.

## 추가 결정 — 검사 ERROR가 턴 전체를 버리지 않는다 (2026-09-16)

57턴 배치에서 4턴이 통째로 실패했는데, 원인이 전부 **평가기 결함**이었다.
`<select>`에 `fill`을 수행해 Playwright가 예외를 던졌고(3턴), 해석 불가 정규식 `matrix(1`이
실행 시점에 예외가 됐다(1턴). 한 턴은 요구 13개 중 10개가 PASS였는데 ERROR 3개 때문에
전부 버려졌다.

**정책을 뒤집는다.** 검사는 매번 새 페이지에서 독립 실행되므로 하나가 깨져도 나머지 관측은
유효하다. Q1은 이미 분모에서 ERROR 요구를 빼고 있으므로 턴 전체 폐기는 중복이고, 요구를 많이
뽑은 턴일수록 ERROR를 만날 확률이 높아 모집단이 체계적으로 편향된다. 필수 검사가 **전부**
ERROR일 때만 턴을 실패로 본다.

함께 고친 것: `fill` 대상이 `<select>`면 옵션 선택으로 수행, 해석 불가 정규식은 컴파일러가
거절(`UNSUPPORTED_PROBE`), 실행 단계에서도 예외 대신 불충족 처리.
