# Edu Vibe — K-12 바이브코딩 실습·학습관리 플랫폼

국내 K-12(1차 타겟 중등) 대상으로 **AI 바이브코딩 실습 환경과 학습관리를 결합한** goorm의 교육 플랫폼.
교사가 학급과 수업을 만들고, 학생이 입장 코드로 들어와 AI와 대화하며 HTML 결과물을 만들고 제출하면,
교사가 학급 단위로 결과물과 **프롬프트 과정까지** 확인한다.

레포는 둘, `edu-vibe-front`와 `edu-vibe-server`이고 **둘 다 내가 소유**했다.
2026-09-17 학교 시연이 첫 목표였다.

## 내 역할

**아키텍처를 설계했고, 그 설계대로 양쪽 레포를 구현했다.**

- V2 Tech Spec, DB 스키마 문서, API 명세를 직접 작성했다. **AI는 저자가 아니라 비판적 리뷰어로 썼다.**
- MVP 단계에서 정했지만 **이 구조 그대로 정식 서비스로 올라간다.**
  결정과 기각 근거 전문은 [[2026-09-09-edu-vibe-architecture]].

## 확정한 구조

| 축 | 선택 | 한 줄 근거 |
|---|---|---|
| 레포 | 프론트 1 + 백엔드 1 | 실습창이 타 팀의 SDK 패키지로 온다는 전제. 책임 분리는 레포가 아니라 모듈 경계로 |
| 서버 | NestJS(Express) + MongoDB + Mongoose + `migrate-mongo` | 전자정부표준프레임워크(Spring) 이관 시 코드 변경이 가장 적다 |
| 프론트 | React 19 + Vite + TS(strict) + Tailwind v4 + Vapor UI + TanStack Query | 단일 패키지, Node 24 |
| 계약 | OpenAPI → FE codegen | `@nestjs/swagger`가 스펙 원천 |
| 실시간 | SSE (교사 패널은 폴링) | 학교망 필터링 장비가 WebSocket Upgrade를 자주 차단 |
| 인증 | 교사 JWT + 학생 단기 JWT, 무계정 | 만 14세 미만 가입 허들이 제품 도입을 막는 조건 |
| 인프라 | k8s + TokenHub(사내 LLM 게이트웨이) + Elastic APM | Redis·MQ 미도입 |

## 기술적으로 다시 이야기할 문제

### 프레임워크를 실험으로 검증하고, 전제가 바뀌자 결론을 뒤집었다

Fastify 도입을 제안하면서 [별도 실험 레포](https://github.com/guppyKoo/Fastify-vs-Express-test)에
동일 API를 Express/Fastify로 각각 구현해 4종 실험을 돌렸다(autocannon 워밍업 5초 + 15초 × 3회 중앙값, p99까지 기록).

결과가 내 원래 주장을 **깎았다**. 순수 프레임워크 오버헤드에서는 1.6배 차이가 났지만
30ms 지연 하나만 넣어도 +1.8%로 붕괴했고, 실제 Atlas 조회에서는 +2.1%였다.
그래서 **"성능은 도입 근거가 아니다"를 내 손으로 측정해 확인하고 문서에 그렇게 썼다.**

남은 진짜 근거는 응답 스키마의 구조적 방어였다 — 같은 실수를 양쪽에 심었더니
Express는 `passwordHash`를 그대로 유출했고 Fastify는 걸렀다. 응답 크기도 32.7KB → 14.1KB.

그럼에도 최종 선택은 NestJS(Express)다. **표준프레임워크 이관 전제가 나중에 들어와 결론을 뒤집었다.**
중요한 것은 스택이 바뀌어도 **실험이 증명한 원칙("경계에서 선언한 스키마가 실수를 막는다")은 보존했다**는 점이다 —
전역 `ValidationPipe`(whitelist/forbidNonWhitelisted), `ClassSerializerInterceptor`(excludeExtraneousValues),
`@nestjs/swagger`, Mongoose `strict: true`로 같은 방어선을 다시 세웠다.

면접에서 말할 지점은 "Fastify를 썼다"가 아니라 **"실험으로 내 제안의 근거를 스스로 반증했고, 그럼에도 남은 가치는 이식했다"**다.

### Prisma를 검토하고 기각한 근거를 시간 민감도로 갈랐다

Prisma의 이점(단일 명세 파일, 정확한 타입 추론, 데이터 계층 강제)은 실재한다고 인정하고 시작했다.
기각 근거 7개 중 **결정을 주도한 것은 하나**다 — Prisma Migrate가 MongoDB를 지원하지 않아
`db push`뿐이고 마이그레이션 이력이 남지 않는다. **DB가 비어 있는 그 시점이 깨끗한 이력을 시작할 유일한 타이밍**이었다.

나머지 여섯은 결정을 지지하되 조건이 바뀌면 되돌릴 수 있는 성격으로 분류하고,
**「Prisma 재검토 조건」을 문서에 명시**했다. 결정을 닫지 않고 **되돌릴 조건과 함께** 남긴 것이 핵심이다.

감수한 손실(CRUD 정적 타입 추론 약화)도 「실제로 감수하는 손실」 절에 그대로 적고,
잔여 리스크를 한 줄로 좁힌 뒤(쿼리 오타·프로젝션 불일치의 조용한 실패) M0 대응 세 가지를 붙였다 —
레포지토리 경계의 Zod, `FilterQuery<T>`를 받지 않는 메서드 시그니처, 메서드당 인메모리 DB 왕복 테스트.

### 프론트 라우팅과 서버 경로를 같은 3중 키로 맞췄다

서버가 `artifactId` 단일 키 대신 `/classrooms/:classroomId/projects/:projectId/artifacts/:userId`를 쓴다.
프론트 라우트가 `/learn/:classId/:studentId/:projectId`이므로 **id 변환 계층이 아예 생기지 않는다.**

대신 URL에 `studentId`가 노출되므로 인가를 두 겹으로 뒀다 — 전역 `JwtAuthGuard`(기본 거부) + `@Roles` 위에,
학생은 토큰의 userId·수업 범위와 경로를 대조하고 교사는 학급 소유권을 DB로 확인한다.
그리고 **프론트에서는 `studentId`를 대조하지 않기로 명시했다** — 보안처럼 보이는 코드가 서버의 인가 누락을 가리기 때문이다.

### 무계정 학생 식별을 unique 제약 하나로 보장했다

학생 id를 `{entryCode}-{nickName}`으로 두어 **동명이인 방지를 DB 레벨에서** 보장했다.
입장은 User·Artifact upsert **한 연산**으로 합쳤는데, 단일 노드 mongod라 트랜잭션이 없어서
쓰기가 두 번이면 중간에 깨졌을 때 "멤버엔 있는데 작업물은 없는" 상태가 조용히 남기 때문이다.

이름은 정규화 후 저장한다(trim + 연속 공백 축약). 안 하면 `"김민준"`과 `"김민준 "`이 다른 학생이 되어
**unique 제약이 공백 하나로 뚫린다.**

**감수한 리스크를 문서에 감수한 것으로 적었다** — 이미 쓰인 이름을 치면 그 사람 작업으로 들어간다.
교실에서 교사 감독이 통제 수단이고, 막는 비용(PIN·명단 등록)이 교사 부담을 늘린다는 판단이다.

### 계약을 글로 먼저 확정하는 방식으로 결함을 잡았다

서버는 구현이 이미 있는 상태에서 시작해 **spec-first**로 갔다 — 명세를 그대로 테스트로 옮기고
전체를 실행해 실패 목록을 구현 갭 목록으로 삼았다. RED 26건에서 시작해 spec 22파일 327테스트,
e2e 7파일 94테스트까지 확장했다.

가장 값이 컸던 것은 테스트가 아니라 **글**이었다. 테스트가 없던 API 15개에 대해 반환 형태·엣지케이스를
먼저 산문으로 썼더니, **테스트를 한 줄도 쓰기 전에 결함 8건이 드러났다** — 유령 작업본이 생기는 부트스트랩,
교사가 학생 대신 도움 요청을 넣을 수 있던 권한 검사, 작업본 없이 대화만 지워지던 초기화 등.
**글은 코드를 끝까지 읽게 만들고, 테스트는 예상한 경로만 훑는다.**

완료 기준도 만들었다 — **HTTP 동작·DB 인덱스·직렬화 결과·생성된 OpenAPI·테스트 격리가 같은 계약을 말할 때만 GREEN.**

### AI 협업 구조를 의도적으로 설계했다

기획하는 모델과 RED를 GREEN으로 바꾸는 모델을 **의도적으로 다르게** 썼다.
실행 모델에는 확정된 테스트·명세·재현 명령만 전달하고 기획 과정의 가설과 누적 대화는 전달하지 않았다.
**계획을 세운 모델이 그대로 구현하면 자기가 예상한 방향으로 실패를 해석한다.**
완전한 독립 검증은 아니지만(테스트 자체에 앞선 결정이 들어 있다), 계획 밖의 문제 두 건을 실행 단계에서 찾아냈다.

회고도 모델별 관점을 지우지 않고 나란히 남겼다 — 같은 사이클을 Opus 64점, GPT 68점으로 다르게 채점했고,
차이가 사실관계가 아니라 **가중 방식**에서 온다는 것까지 적었다.

## 정직하게 적어야 할 것

**만드는 힘은 충분했고, 만든 것을 지키는 장치가 약했다.** 스스로 매긴 점수도 그렇게 나왔다
(프론트 61/100, 서버 64/100 — 둘 다 하위 항목이 **테스트와 계약**).

- 프론트 자동화 테스트 **0건**. Vitest 도입 계획(Vite 8 호환 Vitest 4, MSW로 인터셉터까지 실제 경로 검증)까지 세우고 일정상 보류했다.
- `openapi.json`이 실제 동작과 어긋나는 곳이 있어 **아직 계약으로 승격하지 못했다.** codegen은 그다음이다.
- 테스트 하네스가 모듈 평가 순서 때문에 로컬 DB에 연결돼 **정리 코드가 로컬 데이터를 지웠다.**
  두 겹 가드로 회복했지만 사고가 실제로 났다 — 자세한 것은 [[nestjs-e2e-test-harness]].
- 확정한 결정(`sort` 파라미터) 하나가 테스트에도 구현에도 들어가지 않은 채 모든 검증을 통과했다.
  **어떤 검증도 「빠진 것」은 잡지 못한다.**
